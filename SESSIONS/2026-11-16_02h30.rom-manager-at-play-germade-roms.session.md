## Why the owner does not see the phone panels at play.germade.dev/roms/

play.germade's `/roms/` is still **its own manager** (`src/roms/`, ~1 100 lines in rom-manager's
look) over **its own library** (`library/<system>/`). rom-manager 0.2.x, with the panels, is only
on GitHub Pages. The swap was agreed (base `/roms/`, one library) but not built.

## What swapping means: play.germade's manager does things rom-manager does not (yet)

| play.germade's `/roms/` today | rom-manager |
| --- | --- |
| **Mods**: IPS / BPS / UPS imported one by one, auto-assigned by source CRC, renamed, assigned / unassigned, "Jugar con el mod" | none (it was "step 3" of the last session) |
| **Engine per system and per game** ("Motor por defecto") | none (a launcher concern) |
| **"Jugar"** → `/<system>/?game=…&version=…` | none |
| Neo Geo sets against fbneo's dataset, the BIOS (`neogeo.zip`) | NEOGEO romset validation by member checksums (its own DATs) |
| content-addressed files + `index.json` (games → versions with sha1, mods, core) | `<System>/<file>` + `.meta/` (per-game JSON, covers, `scan.json` hash cache) |

Swapping before these exist would take features away from players. So the swap comes in steps, each
releasable.

## Plan

### A. Mods in rom-manager (the old "step 3")

- **Storage**: `.meta/<System>/mods/<sha1>.<ips|bps|ups>`, outside the ROM folders so that scans
  and organizing never see them. Each game's `.meta/<System>/<Game>.json` gets
  `mods: [{ sha1, name, format, sourceCrc, targetCrc?, assignedTo? }]`.
- **Intake**: patches join the existing "Añadir ROMs" intake. BPS / UPS find their game by source
  CRC; IPS by choice (the game that is open, or "sin asignar"). Mods can be renamed, reassigned
  and removed.
- **Details** (desktop) and **panel 4** (phone): the game's mods, with their status (fits a version
  / does not), and "Jugar con este mod" when hosted by play.germade (C).
- The patch parser / applier is small. play.germade's `patch.js` (206 lines) is ported to TS, with
  tests (IPS / BPS / UPS, CRC checks).

### B. The library index for other apps — `.meta/<System>/index.json`

play.germade needs, per system, games → versions (file path, sha1, crc) and their mods, and must not
re-hash or re-group what rom-manager already knows. rom-manager writes **one versioned index per
system** after every change (intake, delete, organize, rename, mods):
`{ "version": 1, "games": { "<gameId>": { "title", "versions": [{ "path", "sha1", "crc", "region", "revision", "verified" }], "mods": [...] } } }`.

**`gameId` = the slug play.germade uses today** (the DAT base title), so the saves that engines keep
in `<engine>/<gameId>/` stay where they are. It is a documented contract in STACK.md, with a test
that pins the shape.

### C. Hosted at play.germade's `/roms/`

- **Build**: `npm run build -- --base /roms/` → `dist-roms/`. The release attaches
  `rom-manager-roms.tar.gz` (the Pages build at `/rom-manager/` stays as it is).
- **Host mode** (only when served under play.germade: a build flag, `VITE_HOST=play.germade`):
  - "Jugar" on a version, and "Jugar con este mod", link to `/<route>/?game=<gameId>&version=<sha1:8>&patch=<sha1:8>`.
    The route comes from a system → launcher-route map (`MegaDrive` → `megadrive`, `SNES` → `snes`,
    `GBA` / `GAMEBOY` / `GAMEBOY COLOR` → the launcher's GBA / GB / GBC routes, `NEOGEO` → `neogeo`).
  - A "← Lanzador" link in the header.
- **One-time migration** of play.germade's library on first open in host mode. If OPFS
  `library/<system>/index.json` exists:
  - its ROMs go through the normal intake, so they are named and placed by the DATs;
  - its patches become mods, assigned to the same games;
  - its game titles renamed by the player are kept in the game's `.meta`;
  - a marker (`.meta/migrated-from-play-germade.json`) is written.

  The old folder is **not** deleted here: play.germade removes it once it reads the new index.
- **COOP / COEP**: already checked (2026-11-15 22:08 note): covers keep working isolated.

  - `I18nService` holds `i18nState`; `t()` reads it, so templates follow the language.
  - `ThemeService` holds `themeState`.
  - `ui/state.ts` is a class with getters over the three stores: a class instance is not
    proxied, and each read is tracked where it happens.
- **jq79 lessons, written down for the next ones**:
  1. A whole module namespace must never become a store variable. Its read-only properties break
     the proxy (TypeError on `REGION_ORDERS`). Destructure the module inside the `$importAll`
     pattern.
  2. `:if` / `:elseif` and `:each` are not combined on one element. Wrap the `:each`, or key a
     single item with `:each="k in [key]"`.
  3. One statement per `@event` expression; more go in a function.
  4. Async work started from a `$:` is deferred (`queueMicrotask`), so it never becomes the
     effect's own dependency.
  5. Reactive objects keyed by file paths are fragile: the keys contain dots, and jq79 notifies by
     dotted path. One such map (`activeMap`) caused an endless re-render. Per-row marks by
     position (`rowMarks`) instead.
  6. `$batch` around multi-write handlers (selection + anchor + game; records + stats + covers;
     the resets on changing tab or going home), as the owner suggested.
  7. Hot loops over thousands of rows read `$toRaw(...)`; only the changes are written through
     the proxy.
  8. An `await` in a component's setup makes every instance render on its own: `Icon` has no
     import, and the system folder (which needs `SystemLogo`) is `SystemFolderIcon`.
- **CSS**: four child-combinator rules around icons also match through jq79's component box
  (`> :where([data-c79-box]) >`, same specificity).

## Extension (2026-11-16 13:50 UTC) — A + B approved ("Ok, dale"); implementation notes

Adds: the go-ahead for A (mods) and B (the library index), and the details settled while reading
the code. Where they differ from the plan above, the reason is given.

- **B first**, because A uses it: a BPS / UPS finds its game by looking its source CRC up in the
  indexes.
- **`helpers/library-index.ts`** (pure, tested): `slugOf()`, which is play.germade's `slug()` letter
  for letter, applied to the game's normalized title, as play.germade does. Also
  `buildLibraryIndex(system, match, mods)`, which turns the matched catalogue into the index.
  - Matched releases give versions with `verified: true` when the release is complete.
  - Files no DAT knows become games named after their file, with `verified: false`.
- **Versions are keyed by CRC32, not SHA-1** (a change to B's shape): the scan cache already holds
  every file's CRC32, and a SHA-1 would mean reading the whole library again. play.germade's saves
  are keyed by `gameId` only, so nothing depends on the version key. `version=<crc32>` replaces
  `<sha1:8>` in C's links.
- **`lib/LibraryIndexService.ts`** writes `.meta/<System>/index.json`:
  - when a system's games are worked out (the grouped view already has the match in hand);
  - after intake, a drop, a delete, organize / undo, a sync, and any change to the mods.
- **Mods, stored per system** (a change to A's storage): `.meta/<System>/mods/<sha1>.<format>`, plus
  one registry, `.meta/<System>/mods.json`. The registry replaces a `mods` list in each game's
  `<Game>.json`, because those records belong to one file, and only exist once the player edits
  it, while a mod belongs to the game (`gameId`).
- **`helpers/patch.ts`**: play.germade's `patch.js` in TS, with tests (IPS with RLE and truncation,
  BPS, UPS, every CRC check). Errors carry a `code` the UI translates; the code itself is in English.
- **Intake**: `.ips` / `.bps` / `.ups` files picked or dropped together with ROMs are split off and
  taken after them, as in play.germade.
  - A BPS / UPS goes to the game whose version has its source CRC.
  - Otherwise it goes to the game on screen, else stays unassigned in the system on screen.
  - With no game and no system, it is refused with a reason.
  - What happened is said in a notice.
- **Details** (desktop, and the phone's game panel, which shows the same details): a "Mods" section.
  - For each mod: its name, its format, and whether it fits a version that is here.
  - Actions: rename, unassign, remove.
  - The system's unassigned mods appear with "Assign to this game".
- Every new string is in `en.yaml` and `es.yaml`.

Adds: the owner's idea (2026-11-16), "y si usamos algo como /roms/roms-sdk.js, que se pueda cargar
desde el loader como módulo y así evitar duplicar lógica". It answers play.germade's open question

**What**: the `/roms/` build also emits `roms-sdk.js`, an ES module at `/roms/roms-sdk.js` (its
chunks under `/roms/assets/`).
- The launcher loads it at run time, as it loads the engine apps:
  `await import(/* @vite-ignore */ '/roms/roms-sdk.js')`.
- It is not bundled into the launcher, so the same pinned release serves both.
- Datasets resolve against `/roms/`, the build's base, as the app's do.

**API** (`src/lib/roms-sdk.ts`, versioned: `export const API_VERSION = 1`; English errors with codes):
- `openLibrary()`: the OPFS library node, the same one the app opens.
- **Reading**:
  - `readIndex(system)` / `readIndexes()`: the `.meta/<System>/index.json` contract.
  - `readFile(path)`: a ROM, or a mod's patch, as bytes.
  - `readRomWithMod(path, modPath?)`: patched in memory (`applyPatch`, with its codes).
- **Adding**: `addFiles(files, { system?, gameId? })`, the app's intake without the confirmation
  step.
  - Zips are opened, and ROMs identified by DAT and placed.
  - Patches become mods, after the ROMs.
  - Indexes are rewritten.
  - ROMs no DAT knows are copied to `system` when one is given, else refused with a reason.
  - It returns `{ added, already, refused, mods }` for the caller to say.
- **Removing**: `removeVersion(path)` (the file, its record, the index) and
  `removeMod(system, sha1)`.
- **Migration**: `migrateFromPlayGermade(onProgress?)`, the same `PlayGermadeMigration.run`. With
  it the launcher migrates on its first start after the switch, with no "open /roms/ once" step.
- No UI, no store, no jq79: services and helpers only. The layer rule allows that, since the SDK is
  lib.

**Build**:
- The `build:roms` Vite config gets a second input, the SDK entry. Its file name is stable
  (`roms-sdk.js`, not hashed), so the launcher can import it by name.
- The release archive carries it, and a check fails the release when it is missing.
