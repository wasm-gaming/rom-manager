# Cloud storage: Google Drive and Box

**Date:** 2026-11-15 12:11
**Topic:** Keep a ROM library in step with Google Drive (and, later, Box), from the browser only where possible
**Status:** Proposal — awaiting approval before any code changes.

Origin: the idea parked in wasm-gaming.github.io `ROADMAP.md` ("ROM sync in rom-manager").

---

## Context (measured, not assumed)

- rom-manager pins `@cloudauthn/vfs-sync@0.1.24` (lockfile). `StorageNode` wraps one `VFSNode`
  over an `FSAAdapter`; nothing else in the app knows which backend is underneath.
- 0.1.24 already ships `GDriveAdapter`. **0.2.0 is published**; `^0.1.24` does not pick it up
  (caret on 0.x). Its `vfs.json` format goes v2 → v3 as a `migratable` step: an existing
  library's `.vfs/` is migrated on first read, so the bump is safe for rom-manager (the only writer
  of those folders). The Drive adapter is identical in both versions.
- `GDriveAdapter.write()` uploads with `uploadType=media` and the whole file as one `Uint8Array`
  (no `writeStream`). The README says so: "resumable/streaming uploads to Drive (uploads buffer
  whole)" is not implemented. A 700 MB disc image would sit whole in memory, and a dropped
  connection restarts it from zero.
- Every dataset entry carries a **SHA-1** (`static/datasets/SNES/dataset.json`: 4256 of 4256).
  Drive returns `md5Checksum` / `sha1Checksum` / `sha256Checksum` and Box returns `sha1` in plain
  file metadata, so an uncompressed ROM in the cloud can be identified **without downloading a
  byte**. (Not zips: Neo Geo romsets and zipped sets still need their members read.)
- The scan cache (`.meta/<system>/scan.json`) reuses a hash only when `size` **and** `mtime` match
  (`LibraryScanService.ts:175`). A file that arrives through a sync gets a new mtime, so a second
  device re-hashes its copy once. Acceptable for a first version; noted below.

### Google Drive vs Box

| | Google Drive | Box |
| --- | --- | --- |
| OAuth from a browser | **Yes** — Google Identity Services token client, public client id, no secret | **No** — the code is exchanged "along with its client secret" ([Box OAuth 2.0 guide](https://developer.box.com/guides/authentication/oauth2)); no PKCE today ([feature request](https://pulse.box.com/forums/909778-help-shape-the-future-of-box/suggestions/50572956-add-pkce-support-for-oauth2-applications)) → a backend holding the secret |
| CORS | REST API is CORS-enabled | `api.box.com` once the origin is allowlisted in the app console ([CORS guide](https://developer.box.com/guides/security/cors)); downloads redirect to `dl.boxcloud.com`, which "does not support Cross Origin Resource Sharing" ([in-browser downloads](https://developer.box.com/guides/downloads/in-browser)); `upload.box.com` reported failing CORS (community forum, 2020) |
| Large uploads | resumable sessions, 256 KiB-multiple chunks | direct upload up to ~50 MB; the chunked API only takes files ≥ 20 MB ([chunked uploads](https://developer.box.com/guides/uploads/chunked)) |
| Server-side hashes | MD5, SHA-1, SHA-256 | SHA-1 |
| Adapter in vfs-sync | `GDriveAdapter` | none |
| Least scope | `drive.file`: only files the app created. Picking an existing folder in the Picker does **not** grant its contents; full `drive` is a restricted scope (Google security assessment) | app-wide `root_readwrite` |

**Consequence:** Google Drive fits the "no server of ours" principle; Box does not, as far as the
docs say today. Box needs a spike before any design is worth writing.

## The model: sync, not a remote library

Two shapes were considered:

- **A. A cloud folder opened as a library**, like a local one. Every scan reads every byte over
  the network (until the SHA-1 shortcut exists), and every organize step is one HTTP rename per
  file. It also needs access to a folder the user made, which `drive.file` does not give.
- **B. Sync (recommended).** The local folder (File System Access) stays the working copy and
  the source of truth for scanning and organizing. A Drive folder is a **peer** kept in step by
  vfs-sync's `sync()`. A second computer syncs that folder down into its own local folder.

B reuses the engine rom-manager already ships, keeps hashing local, and fits `drive.file`
exactly: the app creates the Drive folder, so it can see everything in it. `.meta/` travels with
the library, so covers, metadata and `wizard.json` reach the second device too.

Known limit of B, documented, not solved here: a file the user drops into that folder through
drive.google.com is invisible to the app (`drive.file`). Files go in through rom-manager.

## Plan

### Phase 0 — prerequisites in vfs-sync (the owner's library, `cloudauthn/vfs-sync`)

That repo is not attached to this session; it has to be added, or this goes into rom-manager as
a subclass (see open decision 3).

1. **`GDriveAdapter.writeStream()` with resumable uploads**: `POST …?uploadType=resumable` to get
   a session URI, then `PUT` chunks of 8 MiB (a multiple of 256 KiB) with `Content-Range`. On a
   network error or 5xx, ask the session where it stands (`Content-Range: bytes */<total>`) and
   resume from there, with backoff. `write()` keeps `uploadType=media` below the 4 MiB streaming
   threshold.
2. Cancellation: the adapter's `fetch` is already injectable; rom-manager passes one bound to an
   `AbortController` so a sync can be stopped.
3. Release, then bump rom-manager to `@cloudauthn/vfs-sync@^0.2` and run the suite.

### Phase 1 — Google sign-in (`src/services/CloudAuthService.ts`, new)

- The Google Identity Services script (`https://accounts.google.com/gsi/client`) is loaded
  **only** when the user clicks "Connect Google Drive" — a normal visit loads no third-party code.
- `initTokenClient({ client_id, scope: 'https://www.googleapis.com/auth/drive.file' })`. The token
  lives in memory only, never in localStorage; when it expires (1 h) it is requested again, and
  GIS answers without a popup while the Google session and consent are still there.
- "Disconnect" revokes the token (`google.accounts.oauth2.revoke`) and forgets the link.
- The client id comes from `VITE_GDRIVE_CLIENT_ID` at build time (an OAuth client id is public by
  nature). `build.yml` / `release.yml` read it from a repository variable. Without it the Drive
  button is simply not shown.
- The owner creates it once: a Google Cloud project, the OAuth consent screen (app name, the
  `drive.file` scope), a "Web application" client with authorized JavaScript origins
  `https://wasm-gaming.github.io` and `http://localhost:5173`. Step-by-step goes in
  `docs/cloud.md`.

### Phase 2 — Drive as a sync peer (`src/services/CloudSyncService.ts`, new)

- **Link a library**: the app creates `ROM Manager/<library name>` in My Drive (visible to the
  user, owned by the app under `drive.file`) and stores its folder id with the library's handle.
  `HandleStoreService` gains an optional `cloud: { provider: 'gdrive', folderId, accountHint }`;
  IndexedDB version 1 → 2, existing entries untouched.
- **Sync is a plan first** (design principle): `sync(local, drive, { approveMerge })` hands a
  preview — files up, files down, renames, deletes, bytes, conflicts — to a new `SyncModal`.
  Nothing moves until the user approves it; cancelling leaves both sides as they were.
- **Progress and cancel**: files and bytes done / total; the cancel button aborts the fetch.
- **Conflicts**: listed from `node.conflicts()` and settled in the same modal
  (`resolve(uuid, 'mine' | 'theirs')`). Conflict copies (`<name> (conflict <peer> <id>).<ext>`)
  are kept out of the scan, so a copy never shows up as an extra variant of the game.
- **Manual only**: a sync button in the header, beside the refresh. No background loop in this
  phase.

### Phase 3 — the second device

"Open from Google Drive" on the landing view: list the libraries under `ROM Manager/`, choose an
empty local folder (FSA), sync down. Browsers without `showDirectoryPicker` (Firefox, Safari,
Android, iOS) are out of scope here; their local side would be OPFS — a separate topic, tied to
playing on mobile.

### Phase 4 — Box: spike first, code only if it passes

1. A Box app (OAuth 2.0) with the dev and Pages origins allowlisted.
2. From a test page, check: `fetch` of `api.box.com/2.0/files/:id/content` (follows the redirect
   to `dl.boxcloud.com` — expected to fail CORS), a `Range` read, a direct upload and a chunked
   upload to `upload.box.com`.
3. Decide:
   - content and uploads work cross-origin → the only backend is a token exchange (~50 lines, a
     Cloudflare Worker holding the client secret; Box refresh tokens are single-use, so it
     rotates them);
   - downloads do not → every ROM would have to pass through a proxy of ours (bandwidth, and the
     user's files on our server). Recommendation in that case: **no Box**.
4. Only then a `BoxAdapter` (upstream, `VFSAdapter`): `fileId` from Box ids, `list` through
   `/folders/:id/items?fields=name,size,modified_at,sha1`, `readRange` with `Range`, direct upload
   ≤ 50 MB and chunked above (session part size, SHA-1 digest per part and of the whole file on
   commit), `tag`/`writeIf` through the etag and `If-Match`.

### Later, not in this proposal

- Identify cloud files from their server-side SHA-1 (shape A, read-only browsing of a Drive
  library) — the dataset already has the SHA-1.
- Scan cache keyed by content hash instead of `mtime`, so a synced copy is never re-hashed.

## The principle that changes

`STACK.md` and `README.md` say today "100% client-side", "files are never uploaded to any remote
server". They become: **files leave the machine only when the user connects a cloud account and
approves a sync, and only to that account.** For Drive no server of ours is in the path. Box,
if it happens, would add one — for tokens only.

## Extension (2026-11-15 17:51 UTC) — proposal: mobile layout as snap-scrolled panels

New topic, attached here per AGENTS.md (no new session file unless the owner says "capitular").
**Status: proposal, awaiting approval.**

### What the owner asked

On phones, the ROM Manager becomes a row of full-screen panels navigated with horizontal scroll
snap:

1. **Systems** — the console list (logo, name, game count).
2. **Games** — the chosen system's games (cover, title, region flags).
3. **Game detail** — cover, metadata, checksums, and its **versions** (the variants: regions,
   revisions, verified / unknown status).
4. **Mods** — patches available for that game (ROM hacking integration).

### Design

- **One scroller, four panels.** `.mobile-panels { display: flex; overflow-x: auto;
  scroll-snap-type: x mandatory; overscroll-behavior-x: contain }`, each panel
  `flex: 0 0 100%; scroll-snap-align: start; scroll-snap-stop: always` with its own vertical
  scroll. Swipe back/forward is native; no gesture library.
- **Selection drives the panels to the right.** Picking a system fills panel 2 and scrolls to it
  (`scrollIntoView({ behavior: 'smooth', inline: 'start' })`); picking a game fills 3; "Mods"
  in the detail fills 4. Panels to the right of the selection are empty placeholders until then,
  so a swipe never lands on stale content.
- **History.** Each step pushes a history entry (`?system=…&game=…&panel=…`), so Android's back
  gesture / browser back walks panels left, and a link opens on the right panel.
- **A slim header** with the current panel's title and a breadcrumb of dots (tap a dot to jump).
- **Same state, another layout.** The panels read the existing signals (library, selection,
  datasets, covers) — no second data path. Desktop keeps today's tree + details layout;
  the switch is a media query (`max-width: 760px` or `pointer: coarse`) plus one component,
  `MobilePanels.tsx`, that reuses `SystemDetails` / `GameView` / `VariantRow` pieces.
- **Versions** live inside panel 3 (a list under the cover), not as their own panel — each row
  shows region, revision and status; tapping one selects the file whose mods panel 4 shows.
- Reduced motion: `scroll-behavior: auto`.

### Two things to decide before building

1. **Where the library comes from on a phone.** rom-manager opens a folder with
   `showDirectoryPicker` (`FSAAdapter.pick()`), which neither Chrome on Android nor Safari on iOS
   has. Options:
   - **(a) OPFS** — the launcher's own library on the same origin (play.germade sub-route), which
     already holds the ROMs the player added; rom-manager reads it read-only on mobile.
   - **(b) File input** — `<input type=file multiple>` (and zips) for one-off identification,
     nothing kept.
   - Recommended: (a), with (b) as the "add ROMs" button that writes into OPFS.
2. **The mods source.** romhacking.net stopped taking submissions in 2024 and published its
   archive; other catalogs exist with different terms. Needed: which catalog, whether its data can
   be bundled as a dataset (like the No-Intro DATs: patch name, target checksum, format
   IPS/BPS/UPS, link), and whether patches are applied here (a BPS/IPS applier is small and
   client-side) or handed to play.germade's `patch=` route parameter, which already exists.

### Steps once decided

1. `MobilePanels.tsx` + CSS, panels 1–3 on the existing data; history wiring; tests for the
   URL ↔ panel mapping.
2. Mobile library source (per decision 1).
3. Mods: dataset + panel 4 (per decision 2).
4. Verify in Chromium with phone emulation (iPhone 13, Pixel 7), both orientations.

## Extension (2026-11-15 18:12 UTC) — the owner's two decisions, and what the mods source allows

**Status: revised proposal, awaiting approval.**

### Decision 1 — the library lives in OPFS (sync to Drive / Box later)

The owner chose OPFS for the library on phones, with Google Drive / Box sync when that topic is
taken up. This needs no new dependency: `@cloudauthn/vfs-sync`, already the storage layer here,
ships `OPFSAdapter` (and `isOPFSAvailable`) next to `FSAAdapter`, plus its Drive adapter and
`sync` — the later sync is the same `VFSNode` on another adapter.

- `StorageNode.initialize()` gains a source: `'folder'` (today's `FSAAdapter.pick()`) or
  `'opfs'` (`OPFSAdapter.open({ path: 'rom-manager/library' })`). Phones (no
  `showDirectoryPicker`) get OPFS only; desktops keep the folder and can choose OPFS too.
- ROMs come in through `<input type="file" multiple>` (and zips, as the intake already handles)
  and are written into the OPFS library — the intake/organize plan-first flow is unchanged, it just
  runs on another adapter.
- Shared with play.germade's library only when both are served from the same origin
  (play.germade.dev); on GitHub Pages rom-manager has its own. The two libraries keep their own
  layouts for now (rom-manager: organized folders; play.germade: content-addressed); unifying them
  is a later step, best decided together with the sync.
- STACK.md's "Zero Backend / never uploaded" stands: OPFS is still the browser.

### Decision 2 — mods: scrape ROMhacking.net, publish JSON on GitHub Pages

What was found trying it from this session:

- **romhacking.net answers automated requests with a Cloudflare challenge** ("Just a moment…",
  HTTP 403); `robots.txt` also disallows `/download/`. Getting past the challenge with a
  headless browser would be circumventing their bot protection — not something this project
  should do. A scheduled scraper from GitHub Actions is therefore not viable as such.
- **The site is frozen**: it stopped taking submissions in 2024, and an export of its database
  was published on archive.org (`romhacking.net-20240801`: `romhacking.sql.zip`, 6.8 MB, the SQL
  of the hacks / translations / homebrew sections; plus a 12.5 GB zip of the files). That item is
  **restricted** (HTTP 401 without an archive.org login), so CI cannot fetch it either.
- Since nothing new is published there, a periodic scrape would not add anything over a one-time
  import of that export.

Proposal:

1. **One-time import.** The owner downloads `romhacking.sql.zip` (logged in to archive.org) and
   drops it in `.tmp/`; `scripts/build-romhacks.mjs` converts it into
   `static/romhacks/<System>.json` (System = the dataset folder names: SNES, MegaDrive, GBA,
   GAMEBOY, GBC…). Per entry: id, title, kind (hack / translation / homebrew), author(s), version,
   release date, short description, language, **target ROM checksums (CRC32 / SHA-1, as the hack
   page lists them)** and the romhacking.net page URL. Patch files are **not** rehosted: the
   entry links to its page.
2. **Deployed with the app** (the release workflow already uploads `dist-app` to Pages), so it
   is served at `https://wasm-gaming.github.io/rom-manager/romhacks/<System>.json`; GitHub Pages
   sends `Access-Control-Allow-Origin: *`, so play.germade can read it too (or pin it at build
   time, as it does the DATs).
3. **Matching** is by checksum, like the DATs: a game's versions → the hacks whose target ROM is
   one of them. Panel 4 lists those (and says which version each needs).
4. **Applying a mod** stays with play.germade, which already applies IPS / BPS / UPS and plays with
   `?patch=`: rom-manager links "Jugar con este mod" once the player has the patch file;
   rom-manager itself does not download patches.
5. **Periodic updates** — only for sources that offer data without a bot wall (an API, a feed or a
   dump). A scheduled workflow (`romhacks.yml`, weekly) can rebuild and redeploy the JSON from
   such a source when one is chosen; with the RHDN export alone it is not needed.

Open points for the owner: whether the one-time import from the archive.org export is fine (and
downloading it), and whether any other catalog should be a periodic source.

### Order

1. OPFS library source + the mobile panels 1–3 (systems → games → game detail with versions).
   Independent of the mods data, can start once approved.
2. Mods: `build-romhacks.mjs` from the export, the JSON on Pages, panel 4.

## Extension (2026-11-15 18:18 UTC) — OPFS as the base; ROMs and mods imported one by one

**Status: revised proposal, awaiting approval.** Supersedes the mods part of the previous
extension (the RHDN export becomes optional metadata, not the source).

### What the owner set

- **OPFS is the library, everywhere** (phone and desktop). ROMs **and mods** are imported by hand,
  one by one (file picker / drop, zips included), into OPFS.
- **Desktop**: optionally pick a system folder to **sync with** the OPFS library.
- **Later**: the same sync with Box and Google Drive.

### How it maps onto the code

1. **Storage**: `StorageNode` opens `OPFSAdapter.open({ path: 'rom-manager/library' })` by default.
   The folder becomes a second `VFSNode` (`FSAAdapter`) kept in step with `sync()` from
   `@cloudauthn/vfs-sync` — two-way, its conflict naming for files changed on both sides. Drive
   (and Box, once an adapter exists) is then a third node on the same `sync()`: no new
   architecture when that topic comes.
2. **ROM import**: the existing intake (checksum → DAT → plan-first organize) unchanged; it writes
   into OPFS instead of the picked folder.
3. **Mod import**: a dropped `.ips` / `.bps` / `.ups` (or zip with one):
   - BPS / UPS carry the source ROM's CRC32 (and the target's): the mod files itself under the
     game and version it is for, and says when no version in the library fits.
   - IPS carries no checksum: the player picks the game (and version) it belongs to.
   - Stored next to the game (`<System>/<Game>/mods/<file>`, metadata in the `.meta` sidecar:
     name, format, source/target CRC, added date). The parser is play.germade's `patch.js`
     (vendored, same rules) — one implementation of the formats.
   - Panel 4 lists the game's mods; "Jugar con este mod" hands it to play.germade (`?patch=`).
4. **The RHDN export** (if the owner downloads it later) only adds names/authors/descriptions for
   mods the player already has, matched by checksum — optional, not a source.

### Points to take care of

- **Storage eviction**: OPFS is "best-effort" unless `navigator.storage.persist()` is granted;
  Safari on iOS may also clear a site's storage after days without use unless it is installed to
  the home screen. So: ask for persistence on the first import, show the quota
  (`navigator.storage.estimate()`), and recommend installing the app (PWA) on phones; on desktop
  the synced folder is also the backup.
- **Disk space on desktop**: with a folder synced, the library exists twice (OPFS + folder). Fine
  for cartridge systems; for large disc images it doubles the space — worth saying in the UI.
- **Existing users** (who use a folder today): first run offers "importar esta carpeta a la
  biblioteca" — the first sync, with progress — rather than switching silently.
- **Safari's OPFS writes**: `createWritable()` support differs by version; vfs-sync's OPFS adapter
  must be checked on iOS Safari before relying on it there.
- **One library with play.germade**: on the same origin (play.germade.dev) both apps read OPFS.
  Today they use different layouts (rom-manager: organized folders; play.germade: content-addressed
  `library/<system>/`). Recommended: play.germade reads rom-manager's library (rom-manager is the
  manager, play.germade the player), so a ROM or mod is imported once — a follow-up to agree on
  before both grow further.

### Order

1. OPFS as the default storage (+ persistence and quota), import of ROMs one by one; desktop
   folder sync as an option.
2. Mobile panels 1–3 on top of it.
3. Mod import (BPS / UPS auto, IPS by choice) and panel 4.
4. Later: Drive / Box nodes; one shared library with play.germade.

## Note (2026-11-15 18:33 UTC) — the owner on cloud sync and persistence

The owner points out that once Drive / Box are synced, persistent OPFS matters less: a file the
browser cleared can be fetched again from the cloud. For that topic:

- File size limits (checked today): **Google Drive** up to 5 TB per file, 750 GB uploaded per
  user per day (the Drive API has a 1 TB/day per-project cap); **Box** depends on the plan — Free
  250 MB, Personal Pro 5 GB, Business Starter 2 GB, Business 5 GB, Business Plus 15 GB,
  Enterprise 50 GB, Enterprise Plus 150 GB, Enterprise Advanced 500 GB. Cartridge ROMs fit
  anywhere; disc images (PS1 ~700 MB, PSP up to 1.8 GB) do not fit Box Free.
- With a cloud node the library can become a **cache**: the cloud holds everything, OPFS what is
  in use; a missing file is downloaded on demand. vfs-sync syncs whole trees today, so this needs
  "known but not local" entries (placeholders) — a design point for that topic, not for now.
- Until then the persistence request stays: OPFS is the only copy on a phone.
