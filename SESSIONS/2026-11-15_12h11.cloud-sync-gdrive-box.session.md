# Cloud storage: Google Drive and Box

**Date:** 2026-11-15 12:11
**Topic:** Keep a ROM library in step with Google Drive (and, later, Box), from the browser only where possible
**Status:** Proposal — awaiting approval before any code changes.

Origin: the idea parked in wasm-gaming.github.io `ROADMAP.md` ("ROM sync in rom-manager").

---

## Context (measured, not assumed)

- rom-manager pins `@cloudauthn/vfs-sync@0.1.24` (lockfile). `StorageNode` wraps one `VFSNode`
  over an `FSAAdapter`; nothing else in the app knows which backend is underneath.
- 0.1.24 already ships `GDriveAdapter`. **0.2.0 is published**; `^0.1.24` does not pick it up
  (caret on 0.x). Its `vfs.json` format goes v2 → v3 as a `migratable` step: an existing
  library's `.vfs/` is migrated on first read, so the bump is safe for rom-manager (the only writer
  of those folders). The Drive adapter is identical in both versions.
- `GDriveAdapter.write()` uploads with `uploadType=media` and the whole file as one `Uint8Array`
  (no `writeStream`). The README says so: "resumable/streaming uploads to Drive (uploads buffer
  whole)" is not implemented. A 700 MB disc image would sit whole in memory, and a dropped
  connection restarts it from zero.
- Every dataset entry carries a **SHA-1** (`static/datasets/SNES/dataset.json`: 4256 of 4256).
  Drive returns `md5Checksum` / `sha1Checksum` / `sha256Checksum` and Box returns `sha1` in plain
  file metadata, so an uncompressed ROM in the cloud can be identified **without downloading a
  byte**. (Not zips: Neo Geo romsets and zipped sets still need their members read.)
- The scan cache (`.meta/<system>/scan.json`) reuses a hash only when `size` **and** `mtime` match
  (`LibraryScanService.ts:175`). A file that arrives through a sync gets a new mtime, so a second
  device re-hashes its copy once. Acceptable for a first version; noted below.

### Google Drive vs Box

| | Google Drive | Box |
| --- | --- | --- |
| OAuth from a browser | **Yes** — Google Identity Services token client, public client id, no secret | **No** — the code is exchanged "along with its client secret" ([Box OAuth 2.0 guide](https://developer.box.com/guides/authentication/oauth2)); no PKCE today ([feature request](https://pulse.box.com/forums/909778-help-shape-the-future-of-box/suggestions/50572956-add-pkce-support-for-oauth2-applications)) → a backend holding the secret |
| CORS | REST API is CORS-enabled | `api.box.com` once the origin is allowlisted in the app console ([CORS guide](https://developer.box.com/guides/security/cors)); downloads redirect to `dl.boxcloud.com`, which "does not support Cross Origin Resource Sharing" ([in-browser downloads](https://developer.box.com/guides/downloads/in-browser)); `upload.box.com` reported failing CORS (community forum, 2020) |
| Large uploads | resumable sessions, 256 KiB-multiple chunks | direct upload up to ~50 MB; the chunked API only takes files ≥ 20 MB ([chunked uploads](https://developer.box.com/guides/uploads/chunked)) |
| Server-side hashes | MD5, SHA-1, SHA-256 | SHA-1 |
| Adapter in vfs-sync | `GDriveAdapter` | none |
| Least scope | `drive.file`: only files the app created. Picking an existing folder in the Picker does **not** grant its contents; full `drive` is a restricted scope (Google security assessment) | app-wide `root_readwrite` |

**Consequence:** Google Drive fits the "no server of ours" principle; Box does not, as far as the
docs say today. Box needs a spike before any design is worth writing.

## The model: sync, not a remote library

Two shapes were considered:

- **A. A cloud folder opened as a library**, like a local one. Every scan reads every byte over
  the network (until the SHA-1 shortcut exists), and every organize step is one HTTP rename per
  file. It also needs access to a folder the user made, which `drive.file` does not give.
- **B. Sync (recommended).** The local folder (File System Access) stays the working copy and
  the source of truth for scanning and organizing. A Drive folder is a **peer** kept in step by
  vfs-sync's `sync()`. A second computer syncs that folder down into its own local folder.

B reuses the engine rom-manager already ships, keeps hashing local, and fits `drive.file`
exactly: the app creates the Drive folder, so it can see everything in it. `.meta/` travels with
the library, so covers, metadata and `wizard.json` reach the second device too.

Known limit of B, documented, not solved here: a file the user drops into that folder through
drive.google.com is invisible to the app (`drive.file`). Files go in through rom-manager.

## Plan

### Phase 0 — prerequisites in vfs-sync (the owner's library, `cloudauthn/vfs-sync`)

That repo is not attached to this session; it has to be added, or this goes into rom-manager as
a subclass (see open decision 3).

1. **`GDriveAdapter.writeStream()` with resumable uploads**: `POST …?uploadType=resumable` to get
   a session URI, then `PUT` chunks of 8 MiB (a multiple of 256 KiB) with `Content-Range`. On a
   network error or 5xx, ask the session where it stands (`Content-Range: bytes */<total>`) and
   resume from there, with backoff. `write()` keeps `uploadType=media` below the 4 MiB streaming
   threshold.
2. Cancellation: the adapter's `fetch` is already injectable; rom-manager passes one bound to an
   `AbortController` so a sync can be stopped.
3. Release, then bump rom-manager to `@cloudauthn/vfs-sync@^0.2` and run the suite.

### Phase 1 — Google sign-in (`src/services/CloudAuthService.ts`, new)

- The Google Identity Services script (`https://accounts.google.com/gsi/client`) is loaded
  **only** when the user clicks "Connect Google Drive" — a normal visit loads no third-party code.
- `initTokenClient({ client_id, scope: 'https://www.googleapis.com/auth/drive.file' })`. The token
  lives in memory only, never in localStorage; when it expires (1 h) it is requested again, and
  GIS answers without a popup while the Google session and consent are still there.
- "Disconnect" revokes the token (`google.accounts.oauth2.revoke`) and forgets the link.
- The client id comes from `VITE_GDRIVE_CLIENT_ID` at build time (an OAuth client id is public by
  nature). `build.yml` / `release.yml` read it from a repository variable. Without it the Drive
  button is simply not shown.
- The owner creates it once: a Google Cloud project, the OAuth consent screen (app name, the
  `drive.file` scope), a "Web application" client with authorized JavaScript origins
  `https://wasm-gaming.github.io` and `http://localhost:5173`. Step-by-step goes in
  `docs/cloud.md`.

### Phase 2 — Drive as a sync peer (`src/services/CloudSyncService.ts`, new)

- **Link a library**: the app creates `ROM Manager/<library name>` in My Drive (visible to the
  user, owned by the app under `drive.file`) and stores its folder id with the library's handle.
  `HandleStoreService` gains an optional `cloud: { provider: 'gdrive', folderId, accountHint }`;
  IndexedDB version 1 → 2, existing entries untouched.
- **Sync is a plan first** (design principle): `sync(local, drive, { approveMerge })` hands a
  preview — files up, files down, renames, deletes, bytes, conflicts — to a new `SyncModal`.
  Nothing moves until the user approves it; cancelling leaves both sides as they were.
- **Progress and cancel**: files and bytes done / total; the cancel button aborts the fetch.
- **Conflicts**: listed from `node.conflicts()` and settled in the same modal
  (`resolve(uuid, 'mine' | 'theirs')`). Conflict copies (`<name> (conflict <peer> <id>).<ext>`)
  are kept out of the scan, so a copy never shows up as an extra variant of the game.
- **Manual only**: a sync button in the header, beside the refresh. No background loop in this
  phase.

### Phase 3 — the second device

"Open from Google Drive" on the landing view: list the libraries under `ROM Manager/`, choose an
empty local folder (FSA), sync down. Browsers without `showDirectoryPicker` (Firefox, Safari,
Android, iOS) are out of scope here; their local side would be OPFS — a separate topic, tied to
playing on mobile.

### Phase 4 — Box: spike first, code only if it passes

1. A Box app (OAuth 2.0) with the dev and Pages origins allowlisted.
2. From a test page, check: `fetch` of `api.box.com/2.0/files/:id/content` (follows the redirect
   to `dl.boxcloud.com` — expected to fail CORS), a `Range` read, a direct upload and a chunked
   upload to `upload.box.com`.
3. Decide:
   - content and uploads work cross-origin → the only backend is a token exchange (~50 lines, a
     Cloudflare Worker holding the client secret; Box refresh tokens are single-use, so it
     rotates them);
   - downloads do not → every ROM would have to pass through a proxy of ours (bandwidth, and the
     user's files on our server). Recommendation in that case: **no Box**.
4. Only then a `BoxAdapter` (upstream, `VFSAdapter`): `fileId` from Box ids, `list` through
   `/folders/:id/items?fields=name,size,modified_at,sha1`, `readRange` with `Range`, direct upload
   ≤ 50 MB and chunked above (session part size, SHA-1 digest per part and of the whole file on
   commit), `tag`/`writeIf` through the etag and `If-Match`.

### Later, not in this proposal

- Identify cloud files from their server-side SHA-1 (shape A, read-only browsing of a Drive
  library) — the dataset already has the SHA-1.
- Scan cache keyed by content hash instead of `mtime`, so a synced copy is never re-hashed.

---

## The principle that changes

`STACK.md` and `README.md` say today "100% client-side", "files are never uploaded to any remote
server". They become: **files leave the machine only when the user connects a cloud account and
approves a sync, and only to that account.** For Drive no server of ours is in the path. Box,
if it happens, would add one — for tokens only.

## Testing

- Unit (Vitest): `CloudSyncService` against vfs-sync's `MemoryAdapter` and a `GDriveAdapter`
  driven by a fake `fetch` — preview without side effects, approve, cancel mid-transfer, conflict
  listing, conflict copies kept out of the scan. Resumable upload: a session interrupted halfway
  resumes from the offset the server reports.
- Manual, with a test Google account: a small library up; a 700 MB disc image (memory stays flat,
  and a dropped connection resumes); a rename on one side travels as a rename; a conflict.

## Open decisions (owner)

1. **Model**: sync (B) first — recommended — or a cloud folder as a library (A).
2. **Box**: spike first and accept a token-only backend if it passes — recommended — or drop Box.
3. **Resumable uploads**: upstream in `cloudauthn/vfs-sync` (recommended; the repo has to be added
   to the session) or a subclass inside rom-manager.
4. **Google Cloud client id**: created by the owner (needs their Google account).
