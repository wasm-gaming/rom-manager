# 2026-07-30 — Migrating the code to the design in `docs/rom-manager-design.md`

Goal: `docs/rom-manager-design.md` is the source of truth; the code must
converge on it.

## Starting state (verified in the repo)

Implemented:

- `src/services/ChecksumService.ts` — fast CRC32, MD5/SHA1 on demand.
- `src/services/ROMDatasetService.ts` — IndexedDB, flat lookup by hash.
  `DB_VERSION = 3`, `DATASET_FORMAT_VERSION = 5`. Loads **every** dataset
  at startup.
- `src/services/StorageService.ts` — File System Access API via
  `@cloudauthn/vfs-sync`. Hides `.vfs` and `.roms`.
- `src/services/RomLibraryService.ts` — sidecar `.roms/<System>/<Game>.json`.
- `src/services/StoreService.ts` — global state with Preact signals.
- `src/views/ROMExplorer.tsx`, `src/components/FileTree.tsx` — flat explorer.

Not implemented:

- Game ↔ variant grouping (`DatGame`, `GameVariant`, `GameGroup`,
  `parseGameName`, `groupDatGames`, `matchGroupsWithLocalFiles`).
- Wizard mode, `wizard.json`, collections, `.meta/` folder.
- Name normalization.

Verified finding: **no DAT in `libretro-database` includes `cloneof` or
`romof`** (0 matches across the 19 `source.dat` files downloaded). The design's
parent-clone grouping is not viable with this source; No-Intro's parent-clone
DATs can only be obtained manually from DAT-o-MATIC and would break the
automated download. Grouping by base title, which the design already
contemplated as a fallback, is adopted as the only path.

## Closed decisions

| # | Decision |
|---|---|
| D1 | Metadata folder `.meta/` (rename the current `.roms/`). |
| D2 | Mainstream MiSTer retro systems only, using the exact folder name from `Distribution_MiSTer`. Drop GameCube, Wii, PS2, PSP, Dreamcast, C64, Amiga. Add NES, N64, SMS, MegaCD, S32X, TGFX16(-CD), NeoGeo-CD, WonderSwan(Color), PokemonMini. Neo Geo AES/MVS (`NEOGEO`) is left out: its catalog (`romsets.xml`) has no checksums. |
| D3 | **Mixed** structure depending on `media`: cartridge → flat `<system>/<Game>.<variant>.<ext>`; disc → `<system>/<Game>/<variant>/<files>` with a minimal `game.json` as the managed-game marker. Hash cache in `.meta/<system>/scan.json`. |
| D4 | `variantKey = <region>[-<rev>][-<flag>][-<language>][-<crc8>]`, derived from the dataset and never from the local name. `crc8` only on collision, applied to every colliding variant. |
| D5 | A single `normalizeGameName()`: strip `(...)`/`[...]` tags, keep the No-Intro form, NFC, sanitizing identical to libretro's, trim, Windows reserved names, truncate to 120 + `crc8`. The folder/file name thus matches the libretro thumbnail's. |

## Phases

### Phase 1 — Systems and dataset loading

Blocks phases 2 and 3.

- [x] `scripts/systems.mjs`: list per D2, with literal MiSTer names and a
  `media: 'cartridge' | 'disc'` field.
- [x] `scripts/build-datasets.mjs`: `generateIndex()` walks `SYSTEMS` instead
  of scanning the directory, so folders of dropped systems cannot sneak into
  the index; exposes `media` per system.
- [x] Delete the obsolete folders under `static/datasets/` and regenerate: 23
  DATs (13.7 MB), 49,165 covers listed, 55,108 games, 31,646 covers matched.
- [x] `scripts/fetch-covers.mjs`: thumbnails.libretro.com stopped serving the
  directory index (403 with and without `User-Agent`). The listing is now read
  from the `libretro-thumbnails/<System>` repositories via the GitHub API;
  the images are still served from thumbnails.libretro.com.
- [x] `src/services/ROMDatasetService.ts`: `ensureSystem(system)` loads one
  system's dataset on demand, deduplicating in-flight loads;
  `DB_VERSION = 4` clears the stores at startup because the set of systems has
  changed. `MetadataEditor` calls it before every lookup.

No changes to `scripts/dat-to-json.mjs`: with no `cloneOf`, the group key comes
from `normalizeGameName(name)` and `name` is already emitted. Grouping is
computed in the browser (phase 2) and cached in IndexedDB instead of being
precomputed at build time: that way there is a single implementation of
`normalizeGameName` and no drift is possible between the script's and the
app's.

Environment note: the `zsh-proxy` plugin leaves
`http_proxy=http://192.168.88.1:1234` exported, and it does not respond. Any
download script needs `unset http_proxy https_proxy ...` in front.

### Phase 2 — Grouping core (`src/core/rom-grouping.ts`) ✅

Pure TypeScript, no DOM or Node, testable in isolation.

- [x] `DatGame`, `ParsedName`, `GameVariant`, `GameGroup` types.
- [x] `normalizeGameName()` (D5).
- [x] `parseGameName()` — region, language, revision, flags, disc, extras.
- [x] `variantKey()` (D4), including per-group collision resolution.
- [x] `groupDatGames()` — groups by `normalizeGameName(name)`.
- [x] 28 tests with real cases from the DATs: `(^^;`, multi-region,
      revisions, prototypes, discs, NFC, Windows reserved names.

**Result over the 23 real datasets**: 51,216 entries → 26,548 games
(1.9 variants per game) → 41,540 variants, 9,235 of them multi-file,
**0 `crc8` suffixes** and 0 anomalies (no duplicate group ids or variant keys).

**Finding 1 — the DAT lists one entry per file, not per release.** Besides the
Redump discs, many cartridges appear repeated with an identical full name
because the ROM is split across several files. Treating them as distinct
variants made 39% of the keys need a `crc8` suffix. Merging by
name-without-disc-tag brings that down to 9%.

**Finding 2 — unrecognized tags discriminate better than the CRC.** Adding
them as an earlier stage (`Japan-virtualconsole` instead of
`Japan-ABCD1234`) removes the remaining 9% and gives names that are stable
across a re-dump. The design has been updated with this segment.

**Correction to the design**: it was false that the game's folder name matched
the libretro thumbnail's. Thumbnails carry the full DAT name with tags, so the
cover is per variant and `scripts/dat-to-json.mjs` already resolves it.

### Phase 3 — Matching against local files ✅

- [x] `streamCRC32()` in `ChecksumService`, and `calculateCRC32()` rewritten
      on top of hash-wasm.
- [x] `matchGroupsWithLocalFiles()` in `src/core/rom-matching.ts` — which
      variants are present and which are missing.
- [x] `GameCatalogService` — joins dataset + grouping and exposes a folder's
      `GameGroup`s.
- [x] Scan cache in `.meta/<system>/scan.json` (`size` + `mtime` + `crc32`
      per path), disposable and rebuildable.
- [x] `StorageNode.readStream()` and `walkFiles()`; `.meta` added to
      `HIDDEN_DIRS`.
- [x] `ROMDatasetService.listSystemRoms()` with a `system` index (DB_VERSION 5).
- [x] 24 new tests (53 in total).

**The previous CRC32 was useless for this phase**: it walked byte by byte
without a table and required the whole file in memory, so a 700 MB PSX ISO was
not viable. Replaced with hash-wasm, which also offers incremental hashing and
allows streaming reads. Verified against the published check value for
CRC-32/ISO (`123456789` → `CBF43926`), which is the variant the DATs use.

**Matching checks the size as well as the CRC.** CRC32 is 32 bits and a system
has tens of thousands of entries, so a collision is likely, not theoretical. It
has been verified that across the 23 datasets all 51,216 entries have a `size`
field and that **no CRC repeats with different sizes**: the check rejects
nothing legitimate and does protect against an unrelated local file.

**Validation with real data**: with the complete MegaDrive library on disk,
1804/1804 games complete and 0 orphan files, in 3 ms. With PSX FF7 and the
European disc 2 missing, the `Europe` variant is left `partial` and the game
stays `complete` because other variants are whole.

**Phase 2 improvement**: a long tag was being truncated mid-word
(`USA-squaresoftonplaystationp`). Whole words are now dropped
(`USA-squaresoftonplaystation`). There are still 41,540 variants with 0 `crc8`
suffixes and 0 duplicate keys.

### Phase 4 — `.meta/` layer and `wizard.json` ✅

Can run in parallel with phases 2 and 3.

- ✅ Rename `LIBRARY_DIR` in `RomLibraryService` and `HIDDEN_DIRS` in
  `StorageService` to `.meta`. Read with a fallback to `.roms` for one version;
  always write to `.meta`.
- ✅ `WizardConfigService` — reads/writes `.meta/wizard.json`. Disk content =
  untrusted input: validate just as `sanitizeCover` already does.
- ✅ Collection-scanning rule per medium: on cartridge, every subfolder is a
  collection; on disc, discriminate by the presence of `game.json`.

**`.roms` → `.meta` migration.** `read()` tries `.meta` and then `.roms`;
`write()` always writes `.meta`, so a record moves itself the first time it is
edited. Two details that are not obvious, and therefore carry tests:

- `remove()` deletes in **both** folders. Leaving the old copy would resurrect
  the record on the next read.
- A corrupted record in `.meta` returns `null` instead of falling back to
  `.roms`: the fallback would restore metadata the user had already edited.

**Phase 3 was scanning too much.** `scanSystem` walked the whole system
recursively, which means it entered collection folders, which the manager must
not touch. Fixed: it now receives the medium and applies the design's rule. On
cartridge it only looks at the root; on disc it descends only into folders with
`game.json` and does not hash the marker itself. A loose file at the root of a
disc system does count — it is an image that is not organized yet, and if it
were not recognized there would be no way to organize it.

`ROMDatasetService.mediaOf()` gives the medium. Checked against
`static/datasets/index.json`: all 23 systems declare a valid medium (5 disc
ones: MegaCD, Saturn, PSX, TGFX16-CD, NeoGeo-CD), so `GameCatalogService` is
never left without knowing how to scan.

**`wizard.json`.** It stores only the exceptions: system folders are wizard by
default, and a folder returned to its default value is deleted from the file
instead of written. That way no stale entries from renamed systems remain.
Absolute paths, or ones containing `..`, are discarded on read.

81 tests green (rom-grouping 29, LibraryScanService 16, WizardConfigService
12, RomLibraryService 10, rom-matching 8, ChecksumService 6).

### Phase 5 — UI: flat mode vs wizard mode ✅

- ✅ Per-folder toggle in `FileTree`.
- ✅ Wizard: groups what is recognized under its `GameGroup` with sibling
  variants; what is not recognized is shown loose.
- ✅ Mode state in `StoreService`, persisted in `wizard.json`.

**The core is pure.** `core/wizard-tree.ts` turns `MatchResult` + a folder's
real listing into rows. Since it touches neither DOM nor disk it can be tested
end to end (12 tests) and validated against the real datasets, which is what
uncovered the problems in the earlier phases.

Two decisions that were implicit in the design and are now explicit:

- **Only games with at least one file present are listed.** This is a file
  explorer, not a catalog. Inside the game every variant is listed, including
  the absent ones, and the missing discs of a partial variant.
- **A folder whose files have all ended up inside a game disappears.** A
  recognized file claims its folder. This is what makes a disc game a single
  row and keeps a collection intact.

Validated over real datasets:

- MegaDrive with the complete library: 3359 files → 1806 top-level rows (1804
  games + the `Favoritos` collection + a loose hack), 8524 nodes, 0 duplicate
  keys, 1 ms.
- PSX organized per D3: the 239 game folders are absorbed by their groups and
  only `Darksoft`, the collection, survives.
- PSX with 19 second discs deleted: 18 groups become partial, with the variant
  showing `ok missing ok`.

**Recorded limitation.** The system is inferred from the first path segment, so
grouping requires opening the root that contains the system folders. If
`MegaDrive/` is opened directly there is no way to know which system it is and
the tree stays flat.

**`FileTree` refactor.** Rows are no longer filesystem entries but a
`VisibleRow` that also accepts game and variant. Synthetic rows carry no path,
and that is exactly what keeps them out of selection, dragging and deletion:
there is nothing on disk to act on.

Grouping hashes the whole system, so the tree header shows progress; without
that the UI looks hung for minutes. While it computes, the flat listing stays
visible.

93 tests green. `npm run build` passes.

### Phase 6 — Canonical organization (destructive) ✅

Last, and behind explicit confirmation.

- [x] Rename/move to the D3 structure via `StorageNode.move`.
- [x] Mandatory preview of the change plan.
- [x] Operation log in `.meta/` so it can be undone.

**The plan is pure, the execution is not.** `core/rom-organize.ts` computes
what would have to move without knowing the filesystem;
`services/OrganizeService.ts` executes it. That separation is what allows
running the 23 datasets through the planner before letting it touch a single
file.

**Deliberately cowardly.** Anything that would depend on execution order or
overwrite something is reported as a conflict instead of resolved by guessing.
The moves that are emitted are ordered so that none clobbers a file that still
has to move; what cannot be ordered is a cycle, and that is reported too.

**False premise found.** The design assumed the DAT's full name identifies a
release. Not always: there are protos and homebrew where two releases share the
`<game>`'s `name` and differ only in the `<rom>`'s date. Grouping merges them
into one variant and both files end up claiming the same destination. That is
93 cases out of ~51,000 entries. It is not fixed in the grouping —that would
touch phase 3, already validated, for 0.18%—: the planner detects it and moves
neither of the two. Documented in the design.

**Validation on real data.** Simulating a user with the complete library under
DAT names: 50,980 moves, 236 conflicts (all from duplicate names), 0 illegal
exFAT characters and, importantly, **the plan is idempotent across the 23
systems**: applying it and planning again yields zero moves. The longest path is
256 characters.

**What a move drags along.** Moving a ROM invalidates things that are not the
ROM: metadata is indexed by its path and moves with it, and `scan.json` is
deleted because its paths stop being true. The undo log is written *before* the
first move, and undo checks each step before taking it.

`ROMDatasetService` opens IndexedDB on import, so `OrganizeService` loads it on
demand; otherwise applying a plan would require a browser and the service would
not be testable.

119 tests green. `npm run build` passes.

### Phase 7 — Covers ✅

- [x] Second matching layer in `scripts/dat-to-json.mjs`: what the exact name
      does not reach is joined by `normalizeGameName` and emitted in the
      dataset's `covers` map.
- [x] `src/core/rom-covers.ts` — which cover corresponds to a game and what the
      saved copy is called. 15 tests.
- [x] `src/services/CoverService.ts` — download and storage in
      `.meta/<system>/`. 13 tests.
- [x] `ROMDatasetService.gameCoversOf()` and `GameCatalogService.coversOf()`;
      `DATASET_FORMAT_VERSION = 6`.
- [x] 23 datasets regenerated.

**Bullet 1 of the plan was already half-done and badly described.** The build
matched covers *entry by entry* by full name; what was missing was the
per-title layer. It is added as a second layer instead of replacing the first,
because `Sonic (Japan)`'s cover is not `Sonic (USA)`'s and losing that would be
a regression. The map only carries the games the first layer does not reach:
742 entries in total, a few KB, against the ~20,000 it would be if it carried
them all.

`dat-to-json.mjs` **imports `normalizeGameName` from `src/core` itself** (Node
24 strips the types from a `.ts` without transpiling). That is what keeps phase
1's promise —a single implementation— now that the build also needs the game
key. It only works because `rom-grouping.ts` imports nothing: Node cannot
resolve a module with extensionless relative imports.

**The finding that decides the phase: `thumbnails.libretro.com` does not send
`Access-Control-Allow-Origin`.** The browser can display those URLs in an
`<img>` but cannot read their bytes, so "download and store in `.meta/`" was
impossible from that origin. The same images live at
`raw.githubusercontent.com/libretro-thumbnails/<Repo>/HEAD/Named_Boxarts/`,
which does send it; verified across the 23 repositories (206 + CORS header).
`HEAD` avoids having to know whether the branch is `master` or `main`, and with
that the change did not require re-scraping `covers.json` —the files already
store `repository`—, only regenerating the `dataset.json` files.

**A game's cover is stored only once.** The name carries the variant segment
exactly when the cover belongs to that release; if it is the game's, Sonic 2's
fifteen variants resolve to the same file instead of downloading fifteen copies
of the same image. The extension comes from the URL and not from the response,
so the name of an already-saved copy can be known without downloading it.

**Browsing is what populates `.meta/`.** There is no bulk download step:
opening a game shows the local copy if it exists and the remote one otherwise,
and in that case it is copied in the background. A failed download returns
`false` and does not break browsing, which is the behavior `RomLibrary.saveCover`
already had.

`RomLibrary.saveCover` now names `<Game>.case.<ext>` instead of
`<Game>.cover.<ext>`: in an organized library that matches the name of the
catalog cover, so a hand-picked one replaces the published one. Old records
store their own name and still resolve.

**Validation with the 23 real datasets**: 19,895 of 26,548 games with a cover
(74.9%), 19,153 by release and 742 by title; 19,895 distinct file names —no
collisions—, 0 illegal exFAT characters, longest name 133 characters and 0
per-game map entries that no game can ask for.

### Phase 8 — A game is a single row ✅

Requested during phase 7: grouped games must not expand in the tree.

- [x] `core/wizard-tree.ts` — the game row no longer has children and carries
      its releases, its files and its cover as data.
- [x] `FileTree` — a single row, with no disclosure; selecting it selects every
      file of the game, and dragging and deleting act on them.
- [x] `RomDetails` — game view: cover, status, and the versions it includes with
      their files; the present ones open the file.

**Making the row non-expandable removes the only route to a specific file**, and
with it metadata editing and on-demand CRC32. That is why the present files in
the details panel are buttons that open the file, with a button back to the
game. Opening one reads nothing from disk: the records and `stat`s of every file
of the game are loaded when it is selected, because the row reports their paths
as the selection.

Versions are listed **present ones first** and absent ones **collapsed**. Catalog
order buries what the user has among the twenty betas they do not — the case
that motivated the change was Sonic 2 with ten.

After seeing it on screen the presentation was adjusted: in the tree the game is
distinguished only by text color (royalblue), and the release count moved to the
details panel, where the present ones are one badge each instead of a `1/15`
counter.

**Bug found by the screenshot.** The three game rows came out with
`drop-target`'s green background and dotted border: the class was decided with
`dropTarget === row.path`, and since a game row has no path, that compared
`undefined` with `undefined` and was true for all of them whenever nothing was
being dragged. It predated this session —it affected variant and absent-file
rows the same way— but was only visible now that the game row takes their place.

`WizardNode` is down to two variants (`group` and `entry`) instead of five:
variant rows and absent-file rows no longer exist in the tree. With them went
the expansion state of the synthetic branches and their rows' CSS classes.

### Phase 9 — One cover per region ✅

Requested after phase 8: there are games with EU, US and JP versions, and also
world ROMs, so a game must be able to store **one cover per region**; each
version must state which regions and which video system it supports; and the
explorer must allow choosing the preference order among the six permutations.

- [x] `core/rom-regions.ts` — the three regions (EU/US/JP), the standards
      (PAL/NTSC), the DAT name table and the six permutations.
- [x] `core/rom-grouping.ts` — the variant declares `regions` and
      `videoStandards` in addition to the `datRegions` its key is built from.
- [x] `core/rom-covers.ts` — `coversOf` gives one cover per region; `pickCover`
      chooses using the preference order; `storableCoversOf` says what to save.
- [x] `scripts/dat-to-json.mjs` — the per-game layer becomes per-region.
- [x] `CoverService.cacheAll` — an initialized game saves all of its regions.
- [x] `wizard.json` — `regionOrder`, and a menu in the explorer header.
- [x] `RomDetails` — which region the cover is from, and what each version
      supports.

**Regions are not read from the DAT's `region` field.** That field is missing in
a third of the NES entries and never says `World`, so it is still read from the
name and only falls back to the field when the name carries no tag. What is new
is translating the dozens of No-Intro names into the three regions the
application reasons about, in a module shared by the browser and the build.

**The video system is the build's and not the country's broadcast standard**,
because what matters about a ROM is whether it runs at 50 Hz or 60: `Hong Kong`
is NTSC —a PAL country with NTSC-J consoles—, `Brazil` is NTSC —PAL-M is 60 Hz—
and `Argentina` is PAL —PAL-N is 50— even though it is in the American market.
The regex inference the build did over the `region` field is gone: it was a
second implementation of the same thing, and a worse one.

**The preference order does not run over the box you have.** It first searches
among the regions the user's files belong to, and the order decides among those;
only if none of them has a cover is the full order walked. That preserves phase
7's decision and gives the order the job that really belongs to it: **the world
release**, a single file that belongs to all three regions, where the order is
the only thing that can decide. The user mentioning world ROMs is what made it
clear the order had to be this and not an absolute.

**When all of a game's regions resolve to the same image** a single cover is
stored, the game's, instead of three identical ones: that is 8,700 `World`
entries out of 55,158. With a single region it is not collapsed, because a game
released only in Japan has a *Japanese* cover and saying so costs nothing — two
tests that failed with the first version of the rule said as much.

The game row carries **every** cover and not the one to show, so changing the
order does not re-read the folder: choosing belongs to the panel.

**Node was not resolving the core's imports.** The build imports
`src/core/rom-grouping.ts` directly and that module now imports
`./rom-regions`, extensionless like everything Vite bundles. Node strips the
types but resolves as ESM, so `scripts/ts-imports.mjs` was needed, a resolution
hook registered with `--import` because an extensionless specifier is resolved
when linking the graph, before any module body runs. The alternative was writing
the application's imports to suit the build scripts.

**The per-game map's `*` key is a last resort and not a duplicate.** The first
version emitted it for every title without an exact match, and that repeated 721
URLs the browser already reached by falling from region to region: `pickCover`
walks the full order before looking at the game's cover. It is now emitted only
when no cover could be placed in any region, which brings the map from 1,799 to
1,078 URLs without losing a single game with a cover.

**Validation with the 23 real datasets**: 19,895 of 26,548 games with a cover
(74.9%), **the same coverage as before splitting it by regions**. Of those,
14,848 with a cover for one region, 2,858 for two and 984 for all three; in
3,787 the preference order changes the image. The per-game map goes from 742
entries to 968 titles and 1,078 URLs (~185 KB in total), with 0 unreachable
entries. The 24,723 possible file names are all distinct, 0 with illegal exFAT
characters and the longest 130 characters.

The copies saved by phase 8 were named `<Game>.<variant>.case.png` and are now
named `<Game>.<region>.case.png`: the old ones are left unused and get
downloaded again. It is a cache, so it is not migrated.

## Order and risks

- Critical sequence: 1 → 2 → 3. Phase 4 can overlap. 6 and 7 at the end.
- Main risk: phase 6 modifies the user's files. It must not run without a
  preview and without an undo log.
- Secondary risk: IndexedDB volume once all the retro systems are added;
  mitigated by phase 1's on-demand loading.
- Covers now depend on `raw.githubusercontent.com`. If that origin were to rate
  limit requests, local saving is lost, not display: pointing `boxartUrl` back
  at `thumbnails.libretro.com` would be enough.
