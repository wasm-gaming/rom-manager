# 2026-07-31 14h17 — Neo Geo AES/MVS (`NEOGEO`): the `.neo` half

Goal: add `NEOGEO` to the closed list of systems, covering the part of it that
fits the "identify by hash" principle — the `.neo` single-file sets — and leave
Darksoft/MAME sets explicitly out.

Continues the closing extension of
[2026-07-30](2026-07-30.rom-catalog-design-migration.md), which established that
the reason recorded for leaving Neo Geo out ("no checksums") was false.

**Nothing is implemented yet.** This file is the plan, for review.

## Starting state (measured, not assumed)

Source: `libretro/libretro-database`, `dat/SNK - Neo Geo.dat` (54 KB), and
`libretro-thumbnails/SNK_-_Neo_Geo`. Numbers produced with
`.tmp/scripts/neogeo-probe.mjs`, which imports the application's own
`parseGameName`, `normalizeGameName`, `variantKey` and `sanitizeName` so they
are the numbers the browser would see.

| Measurement | Value |
|---|---|
| Entries in the DAT | 278, all one `.neo` file, one CRC32, no MD5/SHA1 |
| Distinct CRC32 | 278 (no duplicates) |
| Total size of the library | 9.9 GiB, largest `mslug3.neo` at 90.0 MiB |
| Base titles (`normalizeGameName`) | 205, of which 49 have more than one set (largest: 6) |
| Entries with a region tag | **1** of 278; languages 0; revision 5 (`V-Liner (v0.53)`…); flags 0 |
| Entries with no tag at all | 110 |
| Distinct unknown tags | 122 — `bootleg`, `prototype`, `set 1`, `Korean release`, `NGM-2530`, `NGH-2510`… |
| Published boxarts | 257, matching the DAT name exactly for **236 of 278** (84.9%), reaching 188 of the 205 titles |
| Longest folder name | 100 chars (limit is 120); 0 names with characters exFAT rejects |

`NEOGEO` is confirmed as the folder name in `Distribution_MiSTer/games`, next to
the `NeoGeo-CD` already supported.

### What breaks today

Four concrete things, each verified:

1. **The converter returns zero games.** `dat-to-json.mjs`'s ROM regex requires
   `sha1` (`crc … [\s\S]*?\bsha1\s+…`) and this DAT carries CRC32 only. Running
   it as-is prints `Games: 0  Files: 0`.
2. **The variant key degenerates.** `variantKey` starts from the region, and
   there is none: 278 entries produce **7 distinct keys**, and 117 of them
   collide inside their group, so 117 files would be named by their `crc8`.
3. **72 of 278 files exceed `CARTRIDGE_SIZE_LIMIT`** (64 MiB, documented as
   "the largest cartridge ever made", Resident Evil 2 on N64). A quarter of the
   library would be discarded by intake before any lookup.
4. **`neo` is not in `SYSTEMS_BY_EXTENSION`**, so a dropped `.neo` file matches
   no catalogue.

## Decisions to close (proposal)

### E1 — Scope: `.neo` only, Darksoft/MAME out

The core reads `.neo` files, Darksoft sets, decrypted MAME sets and gog sets.
The last three are a folder or a zip of chip dumps declared in `romsets.xml`,
which has no checksums; identifying them means matching a *set* of members
against an arcade DAT (`metadat/fbneo-split/`, 1.8 MB and 10.6 MB) — a second
identification path, and a separate feature.

Consequence to accept: a user with a Darksoft pack sees nothing recognized. That
is already the rule for cartridge systems — an unzipped set is a subfolder and
therefore a collection the manager must not touch ([collections](../docs/collections.md)) —
so only the **zipped** sets sitting at the root of `games/NEOGEO` are a new
case: files that will never match. They stay visible and untouched in flat mode.

### E2 — `dat:` declares its base folder

`dat/SNK - Neo Geo.dat` is not under `metadat/`, the single base
`download-dats.mjs` concatenates. Proposal: the `dat` field of `SYSTEMS` holds
the path from the repository root (`metadat/no-intro/…`, `dat/SNK - Neo Geo.dat`)
and the script stops adding a prefix. It is a one-line change in the script and
a mechanical edit of the 23 existing entries, and it removes a hidden constant.

### E3 — The parser accepts an entry with CRC32 only

`md5` and `sha1` become optional in `dat-to-json.mjs`. Care is needed: making
`sha1` optional inside the current flat regex lets the lazy `[\s\S]*?` run into
the *next* ROM's `sha1` within the same game block. The ROM block has to be
delimited first (balanced parenthesis, as the game block already is) and the
checksums read inside it. This is the one change that touches every system, so
it needs a test asserting an unchanged CRC count on a DAT that does carry SHA1.

### E4 — The variant key is built from the set tags

Measured, on this DAT:

| `variantKey` options | Colliding entries |
|---|---|
| current (`{}`) | 117 in 48 groups |
| `{ extras: true }` | **4 in 2 groups** |

`extras` already exists and already slugs unknown tags, so the machinery is
there; what is missing is that `Unknown` is hardcoded as the first part when
there is no region, giving `Unknown-ngm2530`. Proposal: when a name yields no
region, the key starts at the extras, so the sets read
`Garou - Mark of the Wolves.ngm2530.neo`, `.ngh2530.neo`, `.bootleg.neo`,
`.prototype.neo`. `Unknown` stays for the case with neither region nor extras.

The remaining 4 collisions are two pairs whose tags are identical for the first
24 characters (`hack of The King of Fighters 2001` and its `, alternate`;
`Korean release of Samurai Shodown II, set 1` / `set 2`) — `SLUG_LENGTH` cuts
them at the same point, and the `crc8` suffix resolves them, which is exactly
what it exists for. No reason to raise `SLUG_LENGTH` for two cases.

**This is the decision worth arguing about**: turning `extras` on for a system
promotes an open-ended tag vocabulary to file-name material, and a DAT update
that rewords a tag renames a file. The alternative — a Neo-Geo-specific parser
that only recognizes `NGM-xxxx`/`NGH-xxxx`, `set N`, `bootleg`, `prototype` —
is more stable and more code, and leaves the other 90-odd tags to `crc8`.

### E5 — The cartridge size limit stops being global

`CARTRIDGE_SIZE_LIMIT` encodes "no cartridge is larger than 64 MiB", which Neo
Geo simply falsifies (90 MiB). Proposal: the limit becomes a property of the
system, defaulting to the current 64 MiB, with `NEOGEO` at 128 MiB — the size
of the largest SDRAM module the core's README talks about, which is the real
ceiling. The purpose of the limit is untouched: keeping a `.bin` disc track from
being looked up as a cartridge.

### E6 — `neo` maps to `NEOGEO` only

One line in `SYSTEMS_BY_EXTENSION`. The extension is unambiguous.

### E7 — Neo Geo has no regions, and that is fine

With one region tag in 278 entries, every cover lands as an exact per-entry
match (236 of them) and the game-level fallback lands under `*`. `pickCover`
already walks EU → US → JP → `*`, so it resolves; games show no region badge and
the preference order does nothing for this system. To verify in the UI rather
than assume: that a group whose variants have no region renders without an empty
badge row.

### E8 — Bootlegs, hacks and prototypes stay in the dataset

Roughly 60 of the 278 entries. They are in the DAT, they have a CRC32, and a
user who owns one deserves to see it identified. Filtering the catalogue by
editorial judgement is a different feature and not this one.

## Plan

1. **E2 + E3**: `dat` paths from the repository root and a ROM parser that does
   not require SHA1. Regenerate the 23 current systems and diff the datasets:
   the expected diff is **empty**. This is the safety net for everything after.
2. **E4**: variant key without the `Unknown` prefix, with tests over the real
   colliding cases (`Garou`, `KOF 2003`, `V-Liner`).
3. **E5 + E6**: per-system size limit and the `neo` extension, with an intake
   test for a 90 MiB file.
4. **`NEOGEO` in `SYSTEMS`**: `media: 'cartridge'`, `dat: 'dat/SNK - Neo Geo.dat'`,
   `thumbnails: 'SNK - Neo Geo'`. Full run: `fetch-dat`, `fetch-covers`,
   `to-json`, and check the produced numbers against the table above.
5. **Docs**: `docs/systems.md` gains the row and loses the "is out" section;
   `README.md` loses the todo and says 24 systems; `docs/collections.md` gains
   the zipped-Darksoft case.
6. **Verify in the app**: open a folder with `.neo` files, check identification,
   covers and the wizard's canonical organization.

Steps 1 to 3 are independent of Neo Geo and improve the pipeline on their own;
if the system were dropped afterwards, they would still be worth keeping.

## Risks

- Step 1 touches the parser shared by every system. Mitigated by the empty diff
  over the 23 regenerated datasets, which is a real regression test.
- The GitHub API allows 60 anonymous requests/hour and `fetch-covers` spends two
  per system; a full re-run needs `GITHUB_TOKEN`.
- Adding a system means more IndexedDB, and Neo Geo is small (278 entries).

## Out of scope, on purpose

Identifying Darksoft/MAME sets by their members' checksums. If it is ever taken
on, the note to keep is that `metadat/fbneo-split/FinalBurn Neo (ClrMame Pro
XML, Arcade only).dat` (10.6 MB) does list every chip with its CRC32, so the
data exists; what does not exist is a way to say "this set of files is this
game" in the current model, which matches one file to one entry.

## Extension 2026-07-31 14h34 — sets identified by checksum, not by name

Three answers from review, one of them reopening the scope:

1. `CARTRIDGE_SIZE_LIMIT` goes to 100 MiB globally, instead of the per-system
   limit E5 proposed.
2. A Neo Geo ROM is either a `.zip` or a `.neo`.
3. A game must be recognized **whatever its file is called**, which needs the
   checksums of the set in the dataset.

Point 3 reverses E1, which left Darksoft/MAME sets out. So this extension is the
design for identifying a set by checksum. Measured with
`.tmp/scripts/fbneo-neogeo-probe.py` and `.tmp/scripts/neogeo-identity-probe.py`.

### Applied already (the only code touched so far)

`CARTRIDGE_SIZE_LIMIT` is now `100 * 1024 * 1024`, and its comment no longer
claims the largest cartridge is Resident Evil 2 on the N64. The figure clears
both formats: the largest `.neo` is 90.0 MiB (`mslug3.neo`) and the largest
Neo Geo zip is 81.7 MiB (`garou.zip`). The two tests that name the constant
compute from it, so neither changes. **E5 is closed this way; the per-system
limit is dropped.**

### The mechanism the repo already has

`src/core/zip-directory.ts` reads the central directory of a ZIP and returns
`crc32` per entry, expanding nothing — its own header says that checksum "is the
same the DAT catalogues are keyed by". So identifying a set needs no new
reading, no decompression and no trust in the archive: a few kilobytes off the
tail of the file give the checksum of every member. **What is missing is a
dataset that holds those member checksums**, which is exactly what point 3 says.

### F1 — The source is the FBNeo XML, filtered to `romof="neogeo"`

`metadat/fbneo-split/FinalBurn Neo (ClrMame Pro XML, Arcade only).dat`, 10.6 MB,
Logiqx XML. It carries `romof`/`cloneof`, which the 2026-07-30 session recorded
as absent from every No-Intro/Redump DAT, and that attribute is the only
reliable way to tell Neo Geo apart from MAME's other 6,700 sets.

| | |
|---|---|
| Sets with `romof="neogeo"` | 203 |
| Member rows, BIOS excluded (`merge=`) | 2,007 (9.9 per set, largest 38) |
| Distinct member CRC32 | 1,922, of which 53 appear in more than one set |
| Cost in the dataset | ~96 KB |

BIOS members are dropped on purpose: `sp-s2.sp1` and friends are in every set
and identify nothing.

### F2 — Identification works, and is not ambiguous

Verified over the 203 sets:

- **All 203 signatures** (the sorted multiset of member CRCs) are distinct.
- **All 203 sets** hold at least one member CRC that belongs to no other set.
- The worst case of overlap is a set sharing 57% of its members with another.

So one unique member is enough to name the set, and the rest of the multiset is
confirmation rather than a requirement. Proposed rule: a set matches when the
members present cover it best and at least one of them is unique to it; the
share of members found is reported, so an incomplete set is shown as incomplete
instead of being silently accepted. This works identically for a zip (via the
central directory) and for a folder of loose chip dumps (CRC32 per file, which
the scanner already computes).

### F3 — The identity of a Neo Geo game is the short name

`mslug`, `garou`, `garouh` — MAME's set name, which is also what `romsets.xml`
declares and what the zip and the `.neo` file are called. Measured:

- The 278 `.neo` entries carry **278 distinct short names**; the file name is
  `<short>.neo`.
- The short name joins the two catalogues: 156 games are in both, 122 only as
  `.neo`, 47 only as a set — **325 games** in total.
- Of the 156 shared, the full name agrees in 146 after `sanitizeName`. The other
  10 are wording differences (`Master of Syougi` / `Master of Shougi`,
  `NGM-2640` / `NGM-264?`). **The `.neo` DAT's name wins**, because that is the
  one `libretro-thumbnails` publishes and therefore the one the covers resolve
  against.

**This replaces E4.** The variant key is the short name, not a slug of the
tags: `Garou - Mark of the Wolves.garou.neo`, `.garouh.neo`, `.garoubl.neo`.
It cannot collide, since it is the primary key of both catalogues; it does not
move when a DAT rewords a tag; it needs no `crc8`; and it is the name the user
already sees in `romsets.xml`. The `extras` question of E4 disappears.

### F4 — What the manager may rename, and what it may not

A constraint found in the core's README that changes what "organize" means here:
`romsets.xml` maps a romset **by name**, so the core only loads `mslug.zip` — or
the folder `mslug/` — under that name. Subfolders are allowed for organization,
renaming is not.

So `NEOGEO` splits in two:

- **`.neo` files**: the name is ours. Canonical form `<Game>.<short>.neo`.
- **Sets, zipped or not**: the name is the core's. The manager identifies them,
  shows them with their title and cover, and may move them into a subfolder,
  but **must never rename them**.

That is a first for this project — a system where part of the library is
identified and displayed but not renamed — and it needs saying out loud in
`docs/folder-structure.md` before any organization plan is written.

### F5 — A subfolder that is a set is not a collection

`docs/collections.md` says that for a cartridge system every subfolder is a
collection and is not touched. An unzipped Darksoft set is a subfolder, so under
today's rule it would be invisible. Proposal: for `NEOGEO`, a subfolder whose
files identify a romset is a game; a subfolder that identifies nothing is still
a collection. The discriminant stays a checksum, which is the principle of the
project, and it does not leak into the other cartridge systems.

### The unknown that decides how much of this pays off

The Darksoft pack is **decrypted**, and the DATs describe the original chips.
For the games that shipped encrypted — 67 of the 203 sets are from 1999 on, the
CMC42/CMC50 era — a decrypted set's member CRCs will not match. The pre-1999
majority should match exactly.

This cannot be measured without a pack. It is the one open question worth
resolving before implementing F1–F3, and resolving it costs one drop of a real
Darksoft zip into the app: `zip-directory.ts` already reports the members'
CRC32s, so a handful of them checked against the FBNeo XML answers it.

### Coverage, for expectations

Against the 283 entries of `romsets.xml` (303 names once alternates are split):

| Reachable by | Names |
|---|---|
| `.neo` DAT | 245 |
| FBNeo member checksums | 168 |
| MAME 2015 whole-zip CRC | 237 |
| any of them | 261 of 303 |

The 42 left are homebrew and recent sets (`abyssal`, `gladmort`, `frogfest`,
`cyborgforce`…) that no catalogue lists yet.

The whole-zip CRC of `metadat/mame-nonmerged/` is deliberately **not** used: it
only matches a TorrentZipped zip of that exact MAME version, so it breaks the
moment a set is repacked — which is precisely the "recognize it whatever the
file is" requirement. Member-level matching subsumes it.

### Revised plan

1. E2 + E3 (DAT path from the repository root, parser without mandatory SHA1),
   validated by an empty diff over the 23 regenerated datasets. Unchanged.
2. **The dataset gains sets.** A second kind of entry, `set`, with its members'
   checksums, next to today's one-file-one-CRC entries. This is the real design
   work: `ROMDatasetService` indexes by CRC and a set is N CRCs pointing at one
   game, so the lookup gains a second step (member CRC → set → game) and the
   index gains rows that are not games by themselves.
3. Matching in `RomIntakeService`: members of a zip or a folder → candidate
   sets → best cover with at least one unique member.
4. `NEOGEO` in `SYSTEMS`, `.neo` extension, short name as the variant key.
5. F4 and F5 in the docs before writing the organization plan.
6. The two catalogues joined by short name, with the `.neo` name winning.

Step 2 is where the model changes, and no longer a small feature: today's
dataset says "this CRC is this game", and a set says "these ten CRCs together
are this game". Everything else follows from it.

## Extension 2026-07-31 14h52 — F4 was wrong: the name is ours, and the core can be told

Review answered that a file not matching its name is not a problem, on two
grounds: the dataset should allow renaming it to the *correct* name, and the
manager, backed by the dataset, can tell the emulator which name that is.

Both hold. F4 said sets must never be renamed, and reading
`Main_MiSTer/support/neogeo/neogeo_loader.cpp` shows that is false. **F4 is
withdrawn and replaced.**

### What the core actually does with a name

| Format | Where the name comes from | Verified at |
|---|---|---|
| `.neo` | **The file's own header.** The loader opens it, reads `NeoFile.Name` and shows that; the file name is never used | `neogeo_get_altname` |
| Folder | `<root>/<folder>/romset.xml` if present — the folder carries its own declaration | `neogeo_romset_tx`, `neogeo_get_altname` |
| Folder / zip | otherwise `<parent>/romsets.xml`, otherwise `<root>/<home>/romsets.xml`, and the `<romset name=…>` matched against the folder or zip basename | `neogeo_romset_tx` → `xml_load_files` → `get_romset` |
| Members of a zip | read as `<zip>/<member>`: MiSTer's file layer walks a zip as if it were a folder | `get_name` |

So a `.neo` is already free to be called anything, and a folder or a zip is free
as long as **something declares it** — and that something is a file the manager
writes. `romsets.xml` is not a fixed catalogue handed down by MiSTer; the core's
own README says a MAME set needs "your own XML".

### F4 (replaced) — the manager renames, and writes the declaration

- **`.neo`**: canonical name, no side file. The core reads the title from
  inside.
- **Folder**: canonical name, plus a `romset.xml` inside it declaring
  `<romset name="<that same folder name>">`. Self-contained: the folder can be
  moved, and it keeps working.
- **Zip**: canonical name, plus a `romsets.xml` beside it holding one `<romset>`
  per zip in the folder. A zip cannot carry its own declaration, so this one is
  a per-folder file the manager owns and rewrites.

The identification stays a checksum from end to end: the members' CRC32 name the
romset, the romset gives the canonical title, and the title is what both the
file name and the declaration are written from.

### F6 — The dataset has to carry the hardware attributes

This is what the change costs, and it is a new input. What a romset needs to
*load* is not derivable from any checksum: `cmc`, `pvc`, `sma`, `ms5p`, `ct0`,
`ram`, `xram`, `pcm`, `vromb_offset`, `rom_wait`, `p_wait`. They exist in
exactly one place, MiSTer's own `romsets.xml`, and in no libretro DAT.

Measured over its 283 rows (303 names once alternates are split):

| Attribute | Rows |
|---|---|
| `ram` | 93 |
| `vromb_offset` | 20 |
| `rom_wait` | 17 |
| `p_wait` | 16 |
| `cmc` | 11 |
| `sma` | 8 |
| `pvc` | 6 |
| `ct0`, `xram`, `link`, `pcm`, `ms5p` | 2, 2, 2, 2, 1 |

130 of the 303 names carry at least one; the other 173 need none, and for those
a declaration is just a name and a file list. Of the 325 games in the union of
the two catalogues, **257 have a `romsets.xml` row and 68 do not** — the 68 are
the homebrew and recent sets no catalogue lists either, and a declaration for
them can only be name plus files, which is what the core assumes by default.

So `romsets.xml` becomes a third dataset source, joined by short name, exactly
like the other two. It is 41 KB and it is the only one that is not a checksum
catalogue.

### The boundary that does not move

Renaming stops at the **container**. Inside a set, the member file names are
still load-bearing: with no `<file>` list the core falls back to the Darksoft
convention by name (`prom`, `p1rom`, `srom`, `crom0`, `m1rom`, `vroma0`), and
with a `<file>` list every entry needs either an `index` or a
`type="P|S|C|M|V"`. Those indices exist only in `gog-romsets.xml`, for a subset,
and in no DAT — so the manager renames `mslug.zip` to whatever the canonical
name is, and leaves `201-p1.p1` alone inside it.

That is enough for the requirement as stated: what the user sees and what the
core is told both become ours, and the identity of the game never depends on
either.

### Effect on the plan

Step 5 changes: instead of documenting that Neo Geo cannot be organized, the
canonical organization of `NEOGEO` gains a step that writes a declaration next
to what it renames. Two new pieces of work:

- Emitting `romset.xml` / `romsets.xml` from the dataset, which is a writer with
  no equivalent today — every other system is organized by moving files only,
  and this one leaves a generated file behind. It has to be part of the plan and
  of its undo log, like any other write.
- Carrying `romsets.xml` into the dataset build (F6).

And one question review should settle: whether the canonical name of a set is
the **title** (`Metal Slug - Super Vehicle-001.zip`, consistent with every other
system) or the **short name** (`mslug.zip`, which is what the pack ships and
what every Neo Geo guide on the internet talks about). The declaration makes
both work; only one of them is what the folder should look like.

## Extension 2026-07-31 15h06 — closed: `mslug.zip` on disk, the title in the wizard

Decision from review: a set is stored under its short name (`mslug.zip`) and the
wizard shows it as `Metal Slug - Super Vehicle-001`. Identity by checksum, name
by convention, title by dataset.

### F7 — `NEOGEO` names files `<short>.<ext>`, and nothing else

Every other cartridge system writes `<Game>.<variant>.<ext>`. This one writes
`mslug.zip`, `mslugh.zip`, `mslug.neo` — the short name alone, applied to both
formats for one rule instead of two. It is the only system whose file name is
not built from its title, and the reason is that the name is a key here, not a
label: `romsets.xml` is keyed by it, the pack ships it, and every guide uses it.
The title reaches the user through the wizard row, which is where titles belong.

Consequence for `rom-organize`: the canonical name of a variant becomes a
property of the system rather than a single format string.

### What this decision removes from the plan

The declaration writer of the previous extension. Keeping the short name means
MiSTer's shipped `romsets.xml` already resolves the name, so **the manager
writes nothing**: it identifies, renames to the canonical short name, and
displays. The generated-XML work — a first for the project, with its own undo
log — leaves the critical path and stays available if a later feature wants
titles on disk.

### The picture that emerged while checking it

Splitting "a Neo Geo ROM is a zip or a `.neo`" by what each format can actually
do:

| Format | Identified by checksum | Loads on MiSTer |
|---|---|---|
| `.neo` | **Yes** — `dat/SNK - Neo Geo.dat`, 278 whole-file CRC32 | Yes, natively |
| MAME/gog set (per-chip files, zipped or not) | **Yes** — FBNeo member CRCs, 203 sets, none ambiguous | Only with an XML of your own |
| Darksoft pack (`prom`, `crom0`, `srom`, `m1rom`, `vroma0`) | **No** | Yes, with the shipped `romsets.xml` |

The Darksoft row is a correction to the previous extension, which blamed
encryption and the 67 sets from 1999 on. The problem is worse and simpler: a
Darksoft set does not hold the original chips at all. The loader detects the
format by the presence of `prom` and `crom0` (`dspack` in `neogeo_romset_tx`),
and those are **merged** files — `crom0` is `c1`…`c8` joined, `vroma0` the `v`
roms joined. No per-chip DAT can match them, whatever the era of the game, and
no catalogue publishes their checksums.

So the format the core's README "strongly suggests" is the one the manager
cannot identify by hash. It can only be recognized by its folder name, which is
what this project does not do. Worth saying plainly in the docs rather than
leaving a user to discover it.

The reverse also holds, and is the other half of the irony: the MAME sets that
*are* identifiable are the ones that need a hand-written XML to load. If that
XML is ever generated, note what was measured here — the load type is derivable
from the member's extension (`.p1` → P, `.c3` → C, `.v2` → V) for 82% of the
2,007 members, but 233 are `.bin`, 105 are `.rom` and 30 are `.sp2`, which say
nothing; and 20 of the 203 sets carry two program ROMs, which `type="P"` cannot
tell apart because it always maps to index 4.

### Where that leaves the feature

What ships with F1–F3, F6 and F7: `.neo` files fully managed, MAME sets
identified and shown with their title and cover, Darksoft packs left alone as
what they are. That is a straight win over today, where `NEOGEO` does not exist,
and it does not compromise on identifying by hash.

The drop test on a real Darksoft zip is still worth running, now for a different
reason: to confirm the merged layout rather than to measure how much of it
matches.

## Extension 2026-07-31 15h24 — the flow, end to end

Requested before touching anything: what actually happens, from the build to the
wizard row, and where each piece of this lands in code that already exists.

### 1. Build (node, offline)

`NEOGEO` is the first system with **more than one source**, all three joined by
short name:

| Source | Gives | Rows |
|---|---|---|
| `dat/SNK - Neo Geo.dat` | short name (from `<short>.neo`), title, CRC32 of the whole file | 278 |
| FBNeo XML, `romof="neogeo"` | members with their CRC32, BIOS excluded | 203 sets / 2,007 members |
| MiSTer `romsets.xml` | `altname` and the hardware attributes | 283 |
| `libretro-thumbnails/SNK_-_Neo_Geo` | boxart names, matched by full DAT name | 257 |

`static/datasets/NEOGEO/dataset.json` comes out with the shape it has today plus
one section:

- `list` — the 278 `.neo` rows, `crc → metadata`, exactly as every other system.
- `sets` — new, keyed by short name: `{ title, cover, members: [crc…], attrs }`.

Needed here: E2 (the `dat` path from the repository root), E3 (a parser that
does not require SHA1), a system able to declare several sources, and a reader
for the two XMLs.

### 2. Load (browser)

`ROMDatasetService.ensureSystem('NEOGEO')` fetches that file into IndexedDB. The
`roms` store is keyed by `crc`, which already fits: the 278 `.neo` rows go in as
games, and the 2,007 member CRCs go in as **pointers** — `{ crc, system, set }`,
rows that are not a game by themselves. The sets themselves sit in their own
store, keyed by short name.

`DATASET_FORMAT_VERSION` 7 → 8 and `DB_VERSION` 5 → 6; the upgrade path already
clears and reloads, so nothing is migrated.

One new lookup: members' CRC32 → candidate sets → the one covered best, with at
least one member unique to it (F2 verified there is always one).

### 3. Identify — two doors, one lookup

**Scanning a folder** (`LibraryScanService.scanSystem`). Today every file at the
root is hashed whole and cached by path/size/mtime.

- `.neo` → unchanged: whole-file CRC32, hit in `list`.
- `.zip` → **not** hashed whole. `zip-directory` reads the central directory and
  hands over the members' CRC32 without inflating a byte, and those go to the
  set lookup. This is *cheaper* than what happens today, not more expensive.
- `mslug/` as a folder → `collectFiles` skips every subfolder on a cartridge
  system. F5: for `NEOGEO` its files are hashed and looked up as a set; a folder
  that identifies nothing stays a collection and is not touched.
- The scan cache stores the resolved short name for a set, so opening the folder
  again does not re-read the index.

**Dropping a file** (`RomIntakeService.identify`). Today an archive is opened and
every entry is taken in **on its own** — a zipped game is unpacked, because "an
archive would be a stranger in the library". For Neo Geo that is backwards: the
members are not games. New branch before unpacking: read the central directory,
try the set lookup, and on a hit take the archive **whole** — `apply` copies the
file instead of extracting entries, and it lands as `<short>.zip`. On a miss,
today's behaviour stands untouched.

### 4. Display

`GameCatalogService.catalogueOf` builds the groups and the wizard folds the
recognized files into one row per game. `mslug.zip` and `mslugh.zip` show up
under `Metal Slug - Super Vehicle-001` as two variants keyed `mslug` and
`mslugh` (F3), with the cover the dataset resolved and no region badges (E7).

### 5. Organize

`rom-organize` plans the canonical name, which for `NEOGEO` is `<short>.<ext>`
(F7) instead of `<Game>.<variant>.<ext>`. For a set the plan renames the
container and never touches what is inside it. Nothing is generated: the
`romsets.xml` MiSTer ships already resolves the short name.

### Order of work

1. E2 + E3, validated by an empty diff over the 23 regenerated datasets. No Neo
   Geo involved yet.
2. The dataset format: `sets`, the member rows, the lookup. Testable with
   fixtures, no UI.
3. The two branches of step 3 — a zip taken as a unit, a subfolder read as a
   set.
4. `NEOGEO` in `SYSTEMS`, full build, numbers checked against this file.
5. Naming in `rom-organize`, and the docs.

Steps 1 and 2 carry the risk; 3 is where the behaviour changes for the user; 4
is mechanical once 1–3 hold.

What stays unresolved and does not block: a Darksoft pack cannot be identified
by checksum, because its files are merged and no catalogue lists them.

## Extension 2026-07-31 15h41 — what falls outside, and what a Darksoft pack would settle

### Games left out

Measured against MiSTer's own library, the 283 rows of `romsets.xml`, joined by
short name to the two catalogues (`dat/SNK - Neo Geo.dat` and the FBNeo XML).
`romsets.xml` writes alternate short names comma-joined (`burningfh,brningfh`),

|---|---|

| Same title in a catalogue under another short name (a join to fix, not a gap) | 2 |
| Absent from every catalogue | **25** |

The 25 are one recognizable family and not a random sample: homebrew and modern
releases (`Abyssal Infants` 2021, `Hypernoid` 2021, `Cyborg Force` 2023,
`Captain Barrel!` 2024, `GladMort` and `World Racer` 2025, `Frog Feast` 2005,

entry of its own to load them.

### Would a copy of the Darksoft pack help?

Yes, and it settles three separate questions, only the last of which needs the
whole pack:

1. **Confirm the layout.** That a set is `prom`, `srom`, `crom0`, `m1rom`,
   `vroma0` — merged files, not chips — is inferred from the loader's `dspack`
   detection and from the fallback names it loads. **Two romset folders prove
   or disprove it.**
2. **Find out whether the merged checksums can be derived instead of hashed.**
   If `crom0` is the `c` chips concatenated in a known order, then CRC32 is
   composable — zlib's `crc32_combine` gives the checksum of a concatenation
   from the parts' checksums and lengths, without ever holding the bytes. If
   that holds, **the Darksoft checksums come out of the FBNeo XML and nobody's
   pack needs to ship anything**. If it does not hold — because the sprites are
   interleaved rather than appended, or because the game is one of the
   decrypted ones — only hashing works. **The same two folders answer this**:
   one unencrypted game, one from 1999 on.
3. **Generate the catalogue.** Walking the pack and hashing every file gives
   ~283 sets × ~6 files, a DAT that makes the one currently unidentifiable
   format identifiable by hash. This is the part that needs the full pack.

Two things to decide with eyes open if it goes as far as 3:

- **Reproducibility.** Every dataset in this repo is regenerable by anyone with
  `npm run dataset:fetch-dat` from public sources. A Darksoft-derived DAT would
  be the first committed artifact with no upstream. The mitigation is to keep
  the generating script in the repo, so anyone with a pack can rebuild or extend
  it, and to record which pack version it was built from.
- **Version drift.** If the pack has revisions, the checksums describe the one
  that was hashed and nothing else — the same brittleness that made the
  whole-zip TorrentZip CRC not worth using. Worth knowing the version before
  committing anything.

Checksums are metadata, not content: publishing a list of CRC32s is what every
DAT in this project already is.
